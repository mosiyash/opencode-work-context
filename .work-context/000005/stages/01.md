# Planning

## Goal

Clarify the work goal and constraints

## Prompt

Research and plan a convenient interactive work-context interface for OpenCode without making immediate functional changes. Determine whether a TUI modal for `/wc` actions can open through a safe keyboard shortcut; do not use Ctrl+W without separate confirmation because of terminal and browser conflicts. Also assess contextual argument autocomplete. Before making changes, inspect git status and the current branch, commit only relevant preliminary project changes separately, preserve user changes, and never edit `.work-context` Markdown, JSONL, INDEX, or SESSIONS projections directly.

Study the current architecture: `/wc` is a Markdown command that instructs the agent, the server plugin registers structured `work_context_*` tools, and a separate TUI plugin already uses OpenCode 1.18.x and OpenTUI. Verify the actual installed `@opencode-ai/plugin` APIs for TUI commands, keymap bindings, command palette integration, dialogs, prompt/select controls, and slash-command or autocomplete registration. Establish the capability boundary between package-plugin implementation and changes that would require OpenCode or a public completion hook.

Design a minimal UX without duplicating business logic. The action list must match the existing `work_context_*` tools and their strict mapping in commands/wc.md. Workspace and stage choices must be dynamic. Complex operations such as stage add, rename/update, force-close, and knowledge actions must collect and validate arguments step by step. Mutating actions must display the structured result and stable error code, and dangerous actions require confirmation. Never mutate through direct projection writes or shell commands. Consider two interface levels: a searchable command palette as the reliable first experiment, and true inline `/wc` autocomplete only if the OpenCode API supports it.

The planning-stage result must document feasibility and limitations, explain the chosen shortcut, describe the UX flow and reuse of existing structured tools, and decompose implementation into separate stages. Give every implementation stage a detailed prompt with context, concrete files and actions, constraints, completion criteria, and expected result. Include a test plan for keymap registration, modal open/close, command filtering, dynamic workspace/stage options, argument validation, confirmations, and error handling. Do not begin implementation until the plan and open questions are recorded.
