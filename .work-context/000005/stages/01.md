# Planning

## Goal

Clarify the work goal and constraints

## Prompt

Исследовать и спланировать добавление удобного интерактивного интерфейса для work-context в OpenCode без немедленных функциональных изменений. Цель: определить, можно ли открыть по безопасной горячей клавише (не использовать Ctrl+W без отдельного подтверждения из-за конфликтов терминала/браузера) TUI-модалку действий `/wc` и поддержать контекстный автокомплит аргументов. Перед изменениями проверить git status, текущую ветку и зафиксировать только относящиеся к проекту предварительные изменения отдельным коммитом; не трогать пользовательские изменения и не редактировать вручную `.work-context` Markdown, JSONL, INDEX или SESSIONS-проекции.

Изучить текущую архитектуру: `/wc` сейчас является Markdown-командой-инструкцией для агента, серверный plugin регистрирует structured `work_context_*` tools, а отдельный TUI plugin уже использует OpenCode 1.18.x и OpenTUI. Проверить реальные API установленного `@opencode-ai/plugin` для TUI commands, keymap bindings, command palette, dialogs, prompt/select controls и регистрации slash-команд/автодополнения. Установить границу возможностей: что можно реализовать внутри package plugin, а для чего потребуется изменение OpenCode или публичный completion hook.

Сформировать минимальный UX без дублирования бизнес-логики: список действий должен соответствовать существующим work_context_* tools и их строгому маппингу из commands/wc.md; workspace и stage должны предлагаться динамически; аргументы сложных операций (`stage add`, rename/update, force-close, knowledge) вводятся пошагово с валидацией; mutating actions показывают structured result и stable error code, опасные действия требуют подтверждения. Нельзя выполнять мутации через прямую запись projection-файлов или через shell-команды. Рассмотреть два уровня интерфейса: command palette с поиском действий как надёжный первый эксперимент и настоящий inline autocomplete для `/wc` только если API OpenCode это поддерживает.

Результат planning stage: документированный вывод о реализуемости и ограничениях; выбранная комбинация клавиш с объяснением; UX-сценарий; схема переиспользования существующих structured tools; декомпозиция реализации на отдельные stages. Для каждого implementation stage подготовить отдельный подробный prompt с контекстом, конкретными файлами/действиями, ограничениями, критериями готовности и ожидаемым результатом. Добавить план тестов для keymap registration, открытия/закрытия модалки, фильтрации команд, динамических workspace/stage options, валидации аргументов, подтверждений и обработки ошибок. Не начинать реализацию, пока план и открытые вопросы не зафиксированы.
