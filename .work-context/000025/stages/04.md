# Human-agent Git state coordination

## Goal

Design a clear, low-friction protocol for commits made manually by the user while an agent is actively working in the same stage.

## Prompt

Investigate and design a human-agent Git coordination flow for the case where the user manually commits current-stage work while the agent is still active.

Problem to solve:
- The agent observes tracked changes disappearing from the worktree or HEAD moving during its work.
- It conservatively interprets this as unrelated parallel work, repeatedly runs `git status`, `git log`, `git show`, or broader provenance checks, and loses time even when the user simply committed the shared current work.
- The flow must remain safe in a genuinely shared dirty worktree and must not teach agents to ignore real conflicts or overwrite other work.

Required investigation:
- Review the current standard-mode and startup-mode worktree policies, candidate workflow, session/stage execution state, event boundaries, and any existing Git safety instructions.
- Identify which observations can reliably distinguish a normal user commit of current work from unrelated concurrent edits, rebases, merges, branch switches, resets, or conflicting file changes.
- Consider an explicit lightweight signal from the user, automatic HEAD/worktree checkpoint tracking, a stage-local acknowledgement, commit-range comparison, or a combination. Prefer a flow that is understandable to both the user and agent and does not require repeated expensive inspection.
- Define when one bounded Git check is sufficient, when deeper provenance inspection is justified, and when the agent must stop and ask the user.
- Consider behavior when only some current-stage files were committed, when the commit also contains unrelated files, when HEAD advances without worktree changes, and when multiple agents or sessions are active.
- Do not weaken existing prohibitions on reverting, resetting, amending, or modifying changes the agent did not create without explicit authorization.

Expected result:
- A concise problem model and recommended interaction protocol.
- Concrete user and agent state transitions, including suggested command/tool/UI affordances if needed.
- A decision table separating expected user commits, harmless parallel changes, ambiguous changes, and concrete conflicts.
- Minimal implementation stages with compatibility and migration considerations if a product change is recommended.
- No functional application changes in this stage; record durable architectural decisions only after they are agreed.


## Result

Defined and agreed the `/commited <short-or-full-SHA>` contract for acknowledging a user-created commit during an active agent session. The command uses the abbreviated SHA printed by `git commit`, resolves it to current HEAD, validates the local session checkpoint and attached ref, and advances only that local checkpoint. It remains model-agnostic but uses the light capability tier through each developer's local mapping, avoids standard/deep analysis and primary-agent re-analysis, preserves startup candidate semantics, and stops safely on ambiguous or conflicting Git state. Created implementation stage 05 with the complete implementation and regression-test contract.
