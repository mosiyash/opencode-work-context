# Contracts, Validators, and Git Evidence

## Goal

Define the v1 read-only diagnostic contracts and implement bounded deterministic Git evidence primitives.

## Prompt

Implement the contract foundation and detailed read-only Git primitives for delivery diagnostics. Read the workspace knowledge first and treat it as the authoritative shared contract.

File-level scope:
- `src/errors.js`: add `DELIVERY_INVALID_FINDINGS` and `DELIVERY_DIAGNOSTIC_TOO_LARGE` without changing existing Git/range error meanings.
- Add a focused contract/validation module such as `src/delivery-contracts.js` for contract version constants, strict finding validation, stable-ID validation, limits, completeness helpers, and output-envelope validation.
- Refactor or extend `src/git-candidates.js`, or add a narrowly scoped `src/delivery-git.js`, for detailed immutable-range inspection: normalized final paths, statuses, bounded numstat data, commit hashes, sanitized subjects, per-final-path provenance, and separate rename/copy lineage. Keep candidate mutation primitives behavior unchanged.
- Export only the reusable public/core symbols needed by later stages through `src/index.js` if necessary.
- Add focused tests in a new `test/delivery-contracts.test.js` and/or `test/delivery.test.js`.

Implementation constraints:
- Accept only explicit full lowercase 40-64 hex ancestor endpoints and preserve `GIT_UNAVAILABLE`, `NOT_GIT_REPOSITORY`, `DELIVERY_INVALID_RANGE`, and `DELIVERY_RANGE_TOO_LARGE` semantics.
- Use NUL-safe Git parsing, literal path handling, deterministic ordering, explicit rename/copy flags and similarity threshold from workspace knowledge, no external diff/textconv/color, and bounded aggregate subprocess output.
- Never return raw patches, file contents, command text, environment values, or Git stderr that could disclose sensitive content in the success contract.
- Validate findings structurally only; do not interpret release policy or remediation meaning.
- Keep the existing lightweight `delivery read` behavior compatible unless a deliberate internal primitive replacement is fully regression-tested.

Completion criteria:
- The generic v1 contract and all fixed limits are represented once and validated strictly.
- Detailed Git evidence distinguishes final-path provenance from rename lineage and is deterministic across repeated calls.
- Subject sanitization is UTF-8-safe and bounded.
- All truncation and hard-size conditions are testable and return the agreed completeness state or stable error.
- Candidate mutation code and existing delivery checkpoint behavior remain unchanged.

Focused tests:
- malformed finding shapes, unknown keys, duplicate IDs, invalid severity/stable IDs, path traversal/NUL, count and byte limits;
- non-ancestor/missing/full-hash range behavior and 40/64-character compatibility;
- add/modify/delete/rename/copy statuses, explicit 50% threshold, final-path provenance, merge first-parent behavior, deterministic ordering;
- control/newline/oversize/non-ASCII commit-subject sanitization;
- 500 commit, 500 path, 50 per-path provenance, 4 MiB hard-cap, and no sensitive payload fields.

Expected result: a tested read-only contract and Git evidence foundation ready for explain orchestration, with no tool exposure or diagnostic persistence yet.
