# Vendor-Neutral Capability Profiles

## Goal

Add optional advisory stage capability profiles with user-local model mappings and current-model fallback.

## Prompt

Implement vendor-neutral capability profiles for stages as an optional advisory feature. Read workspace knowledge first and preserve the separation between portable project intent and provider-specific user configuration.

Product contract:
- Supported capability values are exactly `routine`, `implementation`, `architecture`, `security`, and `review`.
- A stage may declare an optional `execution_profile` and optional `review_profile`.
- Project feature mode is `capability_profiles.mode: advisory | off`, defaulting to `advisory` for absent legacy configuration.
- In advisory mode, resume presents the declared capability and resolves an optional user-local mapping. If no mapping exists, continue with the current agent/model without error.
- In off mode, suppress capability presentation, mapping resolution, and missing-mapping warnings while preserving stage metadata unchanged.
- The feature never automatically changes model/agent, never creates a replacement session, never blocks resume, and never writes provider/model identity into tracked workspace data.

File-level scope:
- `src/storage.js`: extend strict project config parsing/defaults for `capability_profiles.mode`; add optional stage metadata fields with strict enum validation and backward-compatible reads for existing stages/configs.
- `src/core.js`: accept profiles during stage creation, provide an explicit update/clear operation, and include advisory profile information in `resume.presentation`/`resume.context` only when enabled. Keep lifecycle behavior unchanged.
- `src/tool-definitions.js` and `tools/`: add structured arguments/tooling for setting or clearing stage execution/review profiles; extend stage creation arguments without breaking existing callers.
- `plugin/work-context.js`, `plugin/server.js`, and `src/opencode-adapter.js`: accept bounded user-local capability mappings through supported OpenCode plugin options or another verified user-local configuration boundary. Do not place provider-specific mappings in tracked `.work-context` projections.
- `commands/wc.md`: document exact structured command mappings for assigning/clearing profiles and explain advisory/off/current-model fallback semantics. Keep this file package-managed.
- `src/stages-snapshot.js`, `src/work-context-snapshot.js`, `src/stages-renderer.js`, and `plugin/stages-tui.js`: expose compact profile metadata where useful without cluttering the sidebar; omit it entirely in off mode.
- `plugin/work-context-modal.js` and switchers: show profile hints only if consistent with existing compact presentation; do not reorder lifecycle state based on profile.
- Update `README.md` and add focused unit/integration/installer tests.

Configuration boundaries:
- Tracked project configuration stores only `mode` and stage capability intent.
- User-local mappings associate capability names with user-defined OpenCode agent/model targets. Validate mapping keys strictly and values as bounded opaque identifiers; do not require OpenAI, Anthropic, Google, or any provider-specific naming scheme.
- Prefer OpenCode-native plugin options if they are supported in both pinned local and managed package activation. Verify how package options are passed to server and TUI plugin entrypoints before choosing the final local mapping location.
- Do not overwrite user mappings during init, activate, or sync-command. Installer-generated project config must remain minimal and provider-neutral.

Resolution contract:
- Stage-specific declared capability is the portable recommendation.
- If advisory mode and a valid local mapping exists, return a recommendation with `source: "mapping"` and the opaque target.
- If advisory mode and no mapping exists, return `source: "current"`, omit unknown agent/model identity, and present: `No mapping configured; continuing with the current model.`
- If mode is off, omit resolution and recommendation fields rather than returning disabled placeholders.
- Invalid project mode or invalid stage profile is a strict configuration/storage error. Invalid user-local mapping must not corrupt tracked state; ignore only the invalid mapping entry with a bounded actionable warning and current-model fallback.
- Because current OpenCode tool context does not authoritatively expose the active loaded model identity, never claim a concrete fallback model unless the host later provides authoritative evidence.

Commands and API:
- Design one explicit structured operation to set or clear `execution_profile` and/or `review_profile` on an existing stage, with optimistic behavior consistent with other stage metadata mutations.
- Extend `stage add` with optional profile fields.
- Ensure omitted fields mean no change during update, while explicit clear removes the field.
- Return canonical profile values and mode without provider-specific runtime details in durable mutation results.

Completion criteria:
- Legacy projects default to advisory mode without migration writes merely from reading/resuming.
- Users can assign, update, and clear execution/review profiles through structured tools and package-managed `/wc` syntax.
- Advisory resume works with mapped and unmapped capabilities; unmapped fallback never errors or blocks work.
- Off mode is behaviorally equivalent to the pre-feature UI/resume experience while preserving metadata.
- Project artifacts remain vendor-neutral; local mappings and runtime target details are not written to tracked projections, knowledge, events, or stage history.
- Pinned local and managed installation paths preserve user options and remain compatible.

Focused tests:
- absent config defaults to advisory; explicit advisory/off; malformed/unknown modes and strict unknown config keys;
- all five profile values, unknown/case-variant values, set/update/partial update/clear, and legacy stage reads;
- resume with mapped execution and review profiles, no mapping fallback, partial mappings, malformed local mapping, and feature off;
- assert no automatic model/session switch and no provider/model persistence in tracked files or event payloads;
- server/TUI plugin options remain project-instance scoped and do not leak across projects or concurrent sessions;
- sidebar/modal output in advisory and off modes, narrow layouts, and no lifecycle/candidate/attention count regressions;
- init, activate, sync-command, wrapper imports, package exports, and command projection consistency.

Run focused tests plus `npm test`, `npm run test:integration`, `npm run test:tui`, `npm run check:language`, and `git diff --check` when implementation is complete.

Expected result: a portable opt-out capability recommendation layer that works with any model provider, gracefully falls back to the user's current model, and leaves model selection under user/OpenCode control.
