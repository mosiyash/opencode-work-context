# ADR, Security, and Integration Verification

## Goal

Finalize architecture, security, compatibility, installer behavior, and end-to-end test coverage for both diagnostic contracts.

## Prompt

Complete the delivery diagnostic feature with architecture/security documentation, compatibility review, installer migration coverage, and end-to-end verification. Do not broaden the product into deployment execution or a generic policy engine.

File-level scope:
- Add a new ADR under `docs/adr/` or update ADR-0008 with a clearly separated accepted decision for explain/doctor contracts, trust boundaries, versioning, evidence provenance, completeness, redaction, and rejected alternatives.
- Update `README.md` with structured examples for delivery explain/doctor, findings supplied by an external planner, limits, truncation, redaction config, direct commits, standard/startup capability differences, evidence kinds, mismatch handling, and both installation repair models.
- Review `commands/wc.md`, package exports, generated projections, installer behavior, and release-facing documentation for consistency.
- Consolidate security and compatibility regressions in `test/delivery.test.js`, `test/delivery-doctor.test.js`, `test/installer.test.js`, `test/integration/plugins.test.js`, and any focused contract/slice test files created by prior stages.
- Update repository language/release notes only if the repository has an established location and the change is required.

Required review:
- Confirm no success/error path exposes raw patches, file contents, environment values, commands from the host, credentials, tokens, secrets, unredacted secret paths, unsafe Git stderr, or arbitrary manifest/config fields.
- Confirm no explain/doctor code mutates candidates, deployment state, work-context projections, config, command files, or diagnostic persistence.
- Confirm strict migration behavior for configs without/with `delivery.secret_path_patterns`, including installer preservation of project-owned config.
- Confirm full-hash 40-64 compatibility, existing range errors, existing checkpoint/read/mark behavior, protocol major/minor rules, all count/byte limits, and recommendation omission on every incomplete case.
- Confirm package-managed command marker/hash survives init, activate, sync-command, npm packaging, and local/managed upgrade guidance.
- Document OpenCode host-attestation limitation and the exact condition under which evidence can become host-attested in the future.

Completion criteria:
- ADR and README accurately describe implemented behavior and explicit non-goals.
- Security review has tests for every prohibited data class and all redaction-bearing output branches.
- Local pinned and managed installation/repair flows are covered and documented.
- Both contracts work end-to-end through core, wrappers, plugin tools, and generated command projection.
- Existing delivery/candidate/lifecycle behavior has no regressions.
- Full repository verification passes: `npm test`, `npm run test:integration`, `npm run check:language`, `npm pack --dry-run`, and `git diff --check`; run `npm run test:tui` if command/TUI package integration is affected.

Focused integration scenarios:
- repository with renames/copies, direct and candidate commits, redacted paths, planner findings, complete recommendation output;
- each truncation/hard-limit path and malformed findings/config;
- standard versus startup workspace;
- stale generated command, stale managed package, stale pinned local package, host attestation unavailable/available;
- repeated diagnostics prove read-only filesystem state.

Expected result: documented, security-reviewed, compatibility-preserving diagnostic contracts with complete installer and integration evidence, ready for an explicit lifecycle/release decision.
