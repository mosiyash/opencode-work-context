# Explain Enrichment and Traceability

## Goal

Build delivery.explain enrichment with provenance, traceability, redaction, and fail-closed completeness.

## Prompt

Implement the core `delivery.explain` operation on top of the validated contracts and detailed Git primitives from the dependency stage.

File-level scope:
- `src/delivery.js`: add read-only explain orchestration while preserving checkpoint read/mark behavior.
- `src/core.js`: add the internal/core entry point only if needed for direct core tests; public tool wiring belongs to a later stage.
- `src/candidates.js`: add a bounded read-only traceability projection if the existing projections cannot safely provide exact-range matching; do not alter candidate lifecycle semantics.
- `src/storage.js`: strictly migrate config parsing/defaults for optional `delivery.secret_path_patterns` using the grammar in workspace knowledge, while preserving existing configs and installer ownership rules.
- Add a small redaction helper module if it keeps path normalization, matching, opaque token assignment, and redaction accounting cohesive.
- Extend `test/delivery.test.js` and config tests (currently primarily `test/notifier.test.js`/`test/installer.test.js`) with focused explain coverage.

Behavior:
- Accept `{ workspace, from, to, findings? }`, validate through the shared contract module, and analyze only that immutable range.
- Return the minimal v1 envelope with normalized path/status/stat evidence, final-path provenance, separate rename lineage, enriched findings, candidate traceability, redactions, limits, summary, and `complete`.
- In startup mode, correlate committed candidate hashes in range and expose bounded candidate/related-stage traceability without ownership claims. Explicitly identify commits with no candidate attribution as direct commits.
- In standard mode, return Git evidence and an explicit candidate-metadata capability state of `unavailable`; do not opportunistically read legacy/local candidate metadata.
- Apply secret-path redaction to every path-bearing output, including echoed finding paths, provenance, lineage, candidate traceability, summaries, and errors/details. Opaque tokens are response-local and deterministic within the response.
- If any semantic limit truncates data, set `complete=false` and omit all recommendation fields. Hard serialized/input/Git byte caps fail with `DELIVERY_DIAGNOSTIC_TOO_LARGE`.
- Do not persist diagnostics, policy, findings, or redaction state.

Completion criteria:
- Complete explain calls produce the v1 success envelope and incomplete calls cannot contain recommendations.
- Findings are normalized and linked only to evidence available in the explicit range.
- Startup and standard capability behavior is explicit and tested.
- Secret paths cannot escape through any output branch or error details.
- Existing delivery read/mark, snapshots, and mode-transition tests remain green.

Focused tests:
- empty and mixed blocking/warning findings, unmatched affected paths, normalized separators/order, duplicate path references;
- startup candidate match, related-stage traceability, direct commits, candidate outside range, standard-mode unavailable capability;
- redaction of final/current/old rename paths and finding paths, response-local opaque correlation, strict malformed config rejection and old-config compatibility;
- each truncation source forces `complete=false` and removes candidate-slice recommendations;
- no writes under `.work-context/local/` or tracked projections during explain.

Expected result: a complete read-only explain core contract with safe provenance, traceability, redaction, and completeness semantics, not yet exposed through the package-managed command.
