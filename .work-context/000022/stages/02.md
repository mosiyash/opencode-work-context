# Support shared startup commits

## Goal

Make startup agents form coherent shared or integration commit candidates for changes related to multiple stages instead of refusing because the worktree has mixed provenance.

## Prompt

Implement shared and integration commit handling for startup-mode workspaces.

Read the active workspace knowledge first. Preserve the established rule that stages do not own files, hunks, candidates, or commits.

Start by reproducing and locating the behavior shown in the reported scenarios: an agent asked to commit in a dirty shared worktree refuses because files contain changes associated with other stages. Determine whether this comes from standard-mode fallback, missing session association, stale resume guidance, command documentation, or candidate API ergonomics. Make the smallest product change that causes an associated startup session to choose a coherent candidate strategy instead of stopping solely because provenance is mixed.

Required behavior:
- Treat commit boundaries and stage boundaries as independent.
- Prefer an exact patch candidate when the intended change is safely separable.
- Support a shared foundation candidate when one coherent change is used by several stages.
- Support an integration candidate when already-intertwined changes cannot be split safely but form one reviewable and testable change.
- Allow one candidate to carry optional references to multiple related stages for traceability. These references must never imply ownership and must not affect stage lifecycle or dependency checks.
- Keep legacy candidate records readable without rewriting them. Validate new metadata strictly and normalize stage identifiers consistently with existing public identifier rules.
- Expose the metadata consistently through structured tools, candidate create/show/list/preview results, command help, and documentation. Avoid adding metadata fields that do not improve the reported workflow.
- Strengthen startup guidance so agents do not ask the user to first commit unrelated stage work merely because complete files are mixed. They must stop only for a concrete patch conflict, an incoherent candidate boundary, or failed required verification.
- Keep standard mode conservative and unchanged.
- Preserve temporary-index publication, ordinary-index isolation, compare-and-swap ref updates, candidate locking, and current stable conflict behavior. Do not infer stage relations from Git history, session history, touched files, or the current diff.
- Keep commit publication explicit; do not auto-commit from hooks, lifecycle operations, or TUI rendering.

Tests:
- Legacy candidate compatibility.
- One candidate related to multiple valid stages.
- Invalid, duplicate, foreign, and malformed stage references.
- Shared/integration metadata round-trips through create, list, show, preview, ready, and commit without changing lifecycle semantics.
- Startup policy directs mixed-provenance work toward candidate formation while standard mode retains its existing behavior.
- End-to-end temporary repository scenario matching the report: multiple stages modify overlapping files, a coherent shared or integration candidate is captured and committed, unrelated WIP and the ordinary index remain unchanged.
- Existing stale patch, overlap, ref-race, hooks/signing, and lock behavior remains unchanged.

Update the accepted startup workflow ADR and user-facing documentation to explain when to use exact, shared foundation, and integration candidates. All repository content must remain in English. Do not edit generated work-context projections directly.

Run focused candidate/core/integration tests, the full relevant test suites, npm run check:language, npm pack --dry-run, git diff --check, and inspect git status. Report the root cause, modified behavior, compatibility decisions, verification results, and any remaining limitation around retrospectively separating edits to the same lines.

Expected result: in startup mode, mixed changes across files or stages no longer cause provenance-based commit refusal; the user can explicitly publish one coherent fast commit related to several stages, while real patch conflicts still fail safely.
