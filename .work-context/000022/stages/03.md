# Persist long-stage execution state

## Goal

Preserve the evolving scope and implementation state of large stages across context compaction, process termination, handoff, and resume without polluting workspace-wide knowledge.

## Prompt

Design and implement a durable stage-local execution ledger for long-running stages whose scope grows through repeated user follow-ups.

Read active workspace knowledge first. Preserve the separation of concerns established there:
- the stage prompt is the durable work contract and original scope;
- workspace knowledge contains only durable facts and decisions useful across stages;
- session summaries describe historical stopping points and handoffs;
- the stage result describes completed work;
- the new execution ledger contains mutable operational state for the current stage.

Product behavior:
- A stage can persist a compact structured execution state containing at least: agreed/current scope, completed items, remaining items, stage-local decisions, blockers or open questions, and pending verification.
- Repeated user follow-ups such as "continue, also add X" can be incorporated without rewriting or losing the original prompt.
- The ledger survives OpenCode process termination, context compaction, session handoff, and resume.
- Resume returns the current execution state prominently enough that the agent continues from it instead of reconstructing work from conversation history.
- The agent guidance requires updating the ledger after meaningful scope changes, important stage-local decisions, completion of substantial work units, discovery of blockers, and before handoff or other likely context boundaries. Avoid an update after every trivial edit or tool call.
- Updates must be explicit structured operations, auditable, idempotent where practical, and safe under the existing storage/write-lock model. Never rely on a background LLM summarizer or unstructured conversation scraping.
- The ledger must remain concise and bounded. Define normalization or replacement semantics that prevent endless append-only growth and stale completed items from overwhelming resume context.
- Stage-local execution data must not be injected into unrelated stages and must not create workspace knowledge automatically.
- Lifecycle operations must not infer completion from checklist state. Stage finish remains explicit under the existing policy, validates or reports remaining ledger work clearly, and preserves a useful final historical record according to a documented rule.
- Existing workspaces and stages without a ledger remain fully compatible and are not rewritten.

API and UX:
- Add clearly named structured tools and matching `/wc` syntax for reading and replacing or incrementally updating execution state. Prefer the smallest coherent API; do not expose direct projection-file editing.
- Include execution state in the human-oriented resume context and instructions without exposing raw internal projections.
- Decide whether a compact progress indicator belongs in existing stage snapshots/sidebar. If added, derive it from stored structured state and keep rendering read-only; do not show a noisy full checklist.
- Provide useful stable errors for malformed state, invalid transitions, size limits, and active-session constraints where applicable.

Investigate the current stage metadata, session event model, projections, resume presentation, prompt generation, storage validation, command parser/help, tool definitions, and TUI snapshot boundaries before selecting persistence format. Prefer canonical structured state with generated projections over parsing arbitrary Markdown. Never manually edit `.work-context` Markdown, JSONL, INDEX, or SESSIONS projections.

Tests:
- Create and update a ledger through several user-added scope items.
- Completed, remaining, decision, blocker, and verification state round-trips correctly.
- Resume in a new session receives the latest compact state after handoff and after simulated process restart.
- Workspace knowledge and unrelated stage resumes do not receive the ledger.
- Original prompt and prior session summaries remain intact.
- Legacy stages resume unchanged.
- Concurrent/stale updates cannot silently lose newer execution state; define revision or replacement behavior explicitly.
- Size and item-count bounds produce stable failures without corrupting state.
- Stage finish behavior with completed and remaining items matches the documented policy and does not auto-finish.
- Any compact TUI indicator remains read-only and degrades safely.

Update README, command/help documentation, and an ADR explaining why execution state is distinct from workspace knowledge, prompts, session summaries, and results. All repository content must remain in English.

Run focused core/storage/session/integration/TUI tests as affected, the full relevant test suites, npm run check:language, npm pack --dry-run, git diff --check, and inspect git status.

Expected result: a large stage can evolve over many turns while maintaining a durable, concise source of truth for what was requested, what has been done, what remains, and what must be verified, even after the original OpenCode process is killed.
