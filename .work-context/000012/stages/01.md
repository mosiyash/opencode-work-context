# Planning

## Goal

Clarify the work goal and constraints

## Prompt

Plan background-session attention notifications for opencode-work-context without making functional implementation changes in this stage.

User scenario:
- A long-running agent task is started in one work-context-linked OpenCode session.
- The user switches to another stage or workspace for parallel work.
- The background session may finish its response, ask a question, request permission, retry, or fail.
- Today the user must repeatedly switch back to discover whether attention is needed.

Agreed product behavior:
1. Track every OpenCode session linked to any Work Context workspace/stage, not only the current workspace.
2. When a linked background session transitions from working to waiting/idle, notify the user even if the response was short. There is no default duration threshold.
3. Questions, permission requests, and errors always require attention.
4. Suppress OS notification when the affected session is currently visible, but retain correct unread/attention semantics for background sessions. If foreground identity cannot be determined reliably, prefer preserving attention over silently missing it.
5. Do not change stage lifecycle automatically. An assistant turn becoming idle does not finish the stage; explicit stage finish rules remain unchanged.
6. Show persistent in-app attention state for missed notifications, clear it when the corresponding native OpenCode session is actually opened, and avoid duplicate notifications for the same event.
7. Notification text should identify workspace/stage and reason without exposing prompts, tool output, secrets, or arbitrary message content.
8. OS notification failures must never break OpenCode or Work Context.

Technical findings already established from installed public APIs:
- OpenCode exposes session.status with busy/idle/retry states and a session.idle event keyed by sessionID.
- question.asked, permission.asked, and session.error events exist; v2-prefixed question/permission variants may also be emitted by some host versions.
- message.updated includes assistant completion/error fields, but session.idle is the preferred whole-turn completion signal.
- The TUI API exposes api.route.current for the foreground session and api.state.session status/question/permission accessors; there is no dedicated foreground-session-changed event.
- Work Context already maps native OpenCode session IDs to all workspaces/stages, persists local-only TUI state in .work-context/local/tui-state.json, and navigates via api.route.navigate.
- Attention state belongs in local TUI state, not canonical workspace/stage metadata or session lifecycle events.
- The TUI plugin is the appropriate owner because it has route/current-session state, navigation, indicators, toasts, and lifecycle cleanup. The server plugin lacks foreground-session knowledge.
- OS adapters can be dependency-free and best-effort: notify-send on Linux, osascript on macOS, and a safe PowerShell approach only if validated. Never use shell interpolation or configurable arbitrary commands.

Planning tasks:
- Verify exact public event subscription behavior and compatibility across the supported OpenCode dependency range.
- Define a pure attention state model, stable deduplication keys, acknowledgement races, restart persistence/pruning, and handling for multiple work-context records sharing one native session ID.
- Decide first-release configuration defaults. The desired product behavior is OS notifications for background attention; unsupported platforms/notifier absence must degrade to in-app attention indicators.
- Decide whether to implement all supported platforms initially or stage Linux first while keeping a portable adapter boundary.
- Define sidebar, stage/workspace/session switcher indicators and sorting without weakening existing navigation behavior.
- Create detailed implementation stages with local prompts, tests, compatibility checks, and documentation requirements.
- Record durable workspace-wide decisions and constraints through knowledge operations so implementation stages do not repeat this investigation.

Do not modify application code in Planning. Do not finish this stage unless the user explicitly requests the lifecycle operation.
