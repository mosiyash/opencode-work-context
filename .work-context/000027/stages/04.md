# Extract shared capability resolver

## Goal

Create a neutral user-level capability mapping component shared by opencode-work-context and project-agent-relay.

## Prompt

RESUME_CONFIRMATION: required

Extract user-level capability depth mappings and resolution from opencode-work-context into a neutral shared project. Do not inspect, create, or modify the new project or either consumer until the user explicitly confirms work after resume.

Target boundary:
- Create a dedicated project at `~/projects/opencode-capability-profiles` unless the user selects another name or location during confirmation.
- Keep stage metadata, capability/depth inference, classifications, review profiles, and workspace lifecycle in opencode-work-context.
- Move only the cross-project user configuration contract and resolver behavior into the shared component.
- Support opencode-work-context, project-agent-relay, and future OpenCode tools without depending on either consumer.

Required design work after confirmation:
- Inspect both consumer projects and their repository instructions before choosing package, release, and integration mechanics.
- Define the canonical depth vocabulary (`light`, `standard`, `deep`) and a versioned configuration schema.
- Define the global user configuration path as `~/.config/opencode/capability-profiles.json`.
- Define a neutral optional project override path, preferably `<project>/.opencode/capability-profiles.json`, without coupling it to `.work-context/`.
- Specify deterministic precedence: explicit invocation override, project override, global mapping, then current-model fallback.
- Decide whether mapping targets remain advisory display labels or include executable OpenCode model identifiers. Do not silently turn advisory recommendations into automatic model selection.
- Provide bounded validation, safe warnings, atomic writes, symlink and regular-file safety, and deterministic resolution results.
- Define a minimal ESM API for read, validate, resolve, configure, show, and reset behavior. Add a CLI only if it materially improves ownership of setup and migration.
- Define ownership of interactive setup so multiple consumers do not implement conflicting writers.

Migration and compatibility:
- Detect existing `.work-context/local/capability-profiles.json` files without silently copying, merging, or deleting them.
- Design an explicit, user-confirmed import path from legacy project-local mappings to global configuration.
- Permit a bounded compatibility fallback where needed, document its precedence, and define removal criteria for a later breaking release.
- Preserve existing `advisory` versus `off` behavior in opencode-work-context unless a deliberate replacement is approved.
- Do not write model/provider identity into tracked work-context stage or workspace data.

Implementation scope after design approval:
- Initialize the new repository with English documentation, package metadata, source, and tests following the local repository standards discovered during inspection.
- Implement the shared schema, storage adapter, resolver, and atomic configuration operations.
- Integrate opencode-work-context with the shared package while preserving its stage-profile contract and existing public behavior.
- Integrate project-agent-relay with the same resolver contract, passing resolved recommendations explicitly rather than requiring target projects to read work-context state.
- Add focused compatibility and integration tests in all affected repositories.
- Update user-facing setup/show/reset documentation and clearly distinguish global mappings from project overrides.

Verification:
- Test global-only, project-override, explicit-override, missing-mapping, invalid-file, legacy-file, symlink, concurrent-write, and reset behavior.
- Verify both consumers resolve identical inputs identically.
- Run each repository's required focused and full checks, including language checks where defined.
- Do not publish packages, create releases, commit, or push unless the user explicitly requests those operations.

Completion criteria:
- One neutral implementation owns the mapping schema and resolution rules.
- Both consumers use the shared resolver without duplicated parsing or precedence logic.
- Existing users receive a documented, confirmation-based migration path.
- Project-tracked metadata remains portable and provider-neutral.
- Verification passes in every modified repository.

Expected result: capability depth mapping becomes a user-level OpenCode concern shared consistently across tools, while opencode-work-context retains only stage-specific profile semantics.
