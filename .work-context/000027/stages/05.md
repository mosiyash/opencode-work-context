# Repository-local commit-all flow

## Goal

Provide a fast, safe Planning flow that commits all intended changes in the current repository and derives traceability and messaging from contributing stages.

## Prompt

Design and implement an explicit repository-local `commit all` workflow for Planning and integration sessions.

Product behavior:
- When the user explicitly requests `commit all`, integrate all intended uncommitted changes inside the current Git repository into one reviewable commit, even when those changes came from several work-context stages.
- Never include changes from external repositories, sibling projects, submodules, separate nested Git repositories, or paths outside the current repository root. Work performed by a stage in another repository must be committed independently there.
- Treat related stages as traceability and commit-message context, never as ownership of files or lines.
- Do not require slow manual partitioning by stage when the user explicitly asked for one repository-wide integration commit.
- Preserve unrelated-change safety: `all` means all intended changes in the current repository, not blindly every filesystem modification. Detect suspicious generated files, secrets, local-only state, and clearly unrelated changes before committing.

Planning and discovery:
- Inspect the existing standard/startup workflow, Git checkpoints, candidate strategies, related-stage metadata, session events, stage results, execution state, dirty-worktree handling, and commit publication code.
- Define the exact command and structured-tool contract. Prefer extending the existing integration candidate flow over creating a parallel commit mechanism.
- Determine contributing stages from deterministic local evidence such as explicit candidate relations, stage session/checkpoint metadata, completed results, and user-selected stages. Do not claim exact provenance when evidence is insufficient.
- If stage attribution is ambiguous, include only defensible stage references or use a workspace-level integration description; do not block a repository-local commit solely because exact per-stage ownership is unavailable.

Candidate construction:
- Resolve and validate the current Git top-level directory before collecting changes.
- Enumerate intended tracked, untracked, renamed, and deleted paths under that Git root.
- Exclude package-local operational state that is not publishable and honor repository ignore rules.
- Detect nested repository and submodule boundaries and exclude their working-tree contents from the parent commit while reporting them separately.
- Create or refresh one `integration` candidate associated with the contributing stages.
- Capture the exact repository-local patch or explicit path set without using the ordinary Git index.
- Preview the candidate and verify that its patch exactly matches the intended repository-local change set before marking it ready.
- Avoid duplicate integration candidates when an active candidate already represents the same commit intent.

Commit message generation:
- Generate the subject from the coherent user-visible result shown by the actual diff, using the repository's recent commit style.
- Use contributing stage titles and results to build an optional concise body that explains the integrated outcomes.
- Do not mechanically concatenate stage titles, include raw workspace/stage identifiers, or mention stages that produced only external-repository changes.
- Allow an explicit user-supplied message to override the generated proposal.

Safety and lifecycle:
- Require an explicit user commit request; stage completion, Planning completion, candidate readiness, tests, or a clean preview must never trigger a commit automatically.
- Inspect Git status, diff, recent log, active Git operations, and candidate state before publication.
- Do not modify or discard unrelated user changes. If the requested all-change boundary is incoherent or unsafe, stop with a precise blocker and preserve the worktree.
- Reuse candidate atomicity, locking, head guards, and stable errors where possible.
- Keep multi-repository coordination informational only; do not attempt a cross-repository atomic commit.

Structured result:
- Return the repository root, included paths, excluded nested/external repositories, contributing stage references and titles, generated or overridden commit message, candidate identity, verification summary, and resulting commit SHA.
- Clearly distinguish `included`, `excluded`, and `unattributed` changes.
- Provide stable errors for no changes, unsafe repository state, incoherent candidate boundary, stale head/checkpoint, nested-repository ambiguity, and failed required verification.

Documentation and tests:
- Update command mappings, tool definitions, startup workflow guidance, help, README, and package-managed command projections through supported generation or synchronization paths.
- Add focused tests for multiple contributing stages in one repository, stage work in an external repository, nested repositories, submodules, untracked and deleted files, ambiguous attribution, unrelated changes, duplicate candidates, message generation, explicit message override, stale Git state, and exact preview-to-commit integrity.
- Verify behavior in both standard and startup modes; document any deliberate mode restriction instead of silently changing semantics.
- Run focused Git/candidate tests, integration tests, the full suite, and the repository language check.

Completion criteria:
- One explicit operation can safely produce a single commit for the intended current-repository changes from multiple stages.
- External and nested repositories are never included in that commit.
- The commit message reflects the actual integrated result and uses stage metadata only as supporting context.
- The final structured result makes inclusion, exclusion, attribution, verification, and commit identity auditable.
- Existing candidate and ordinary commit workflows remain compatible.

Expected result: Planning can quickly publish a coherent repository-wide integration commit without manually separating changes by stage and without crossing Git repository boundaries.


## Result

Implemented a mode-neutral, two-phase repository-local commit-all workflow on top of integration candidates. Inspection is read-only and returns an auditable repository boundary, exclusions, traceability, message proposal, patch verification, and confirmation fingerprint. Confirmed publication re-inspects under the Git lock, rejects stale or unsafe state, preserves the ordinary candidate publication guards, and retains audit metadata across ref compensation races. Added structured tools and wrappers, /wc syntax, protocol evidence, README and ADR documentation, and comprehensive boundary, safety, attribution, race, rollback, standard/startup, and packaging tests. Verification: focused commit-all suite passed 30 tests; full npm test passed 350 tests with 348 passes and 2 expected TUI skips; language check passed for 382 files; npm pack dry run included both new tools; git diff check and command projection synchronization passed; final independent audit found no blocking findings.
